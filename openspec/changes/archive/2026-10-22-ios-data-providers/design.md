# Design

## Context

See `proposal.md` - Why. Phase 0 left a minimal seam: `DataProvider` exposes a single `fetchData(parameters:completion:)`, `JsonRpcDataProvider` wraps `JsonRpcClient`, and `DataHandler` emits lifecycle events while retaining the last result. `Parameters` is a `class` with `let` fields (`region`, `rasterBaselength`, `intervalDuration`, `intervalOffset`, `countThreshold`), so it cannot key a dictionary. `ViewController.defaultServiceEndpoint` hard-codes `http://bo-test.tryb.de`, and `JsonRpcClient` sets a fixed `User-Agent: bo-ios`.

The Android reference splits the same responsibility across `DataProviderFactory` (maps `DataProviderType.HTTP|RPC` to an injected provider), `MainDataHandler` (owns `DataCache`, clears it on source change, assigns a locally-incrementing sequence number per emitted event), and `HttpServiceClientDefault` (`User-Agent: "bo-android" + "-" + longVersionCode`). Two Android facts shape the decisions below: the sequence number is generated by the handler, not sent by the backend, and the HTTP provider is not interchangeable with RPC at the payload level (it returns accumulated strike lists and its grid path is a no-op).

Constraints:

- The Blitzortung HTTP source is plain HTTP (`http://data.blitzortung.org/Data/Protected/...`), so App Transport Security must be relaxed for that host, as it already is for `tryb.de`.
- Android's credential storage is plain `SharedPreferences`; the roadmap design deliberately deviates and requires the Keychain.

## Goals / Non-Goals

**Goals:**

- Make the active source a runtime-resolved choice driven by settings, without a relaunch.
- Keep providers free of caching concerns and put freshness/caching in one place.
- Reuse the existing `data-pipeline` lifecycle events unchanged.
- Derive the client identifier from bundle metadata so no code change is needed per build.

**Non-Goals:**

- Time modes, region/data-area/grid handling, and the time slider (these consume providers but are `ios-data-modes`).
- Clusters. Android's HTTP source explicitly cannot serve them.
- The full preferences screen (Phase 7); this change exposes only the selection surface needed to verify its own scenarios.

## Decisions

### Decision: Resolve the active provider through a factory keyed by settings
Add a `DataProviderFactory` that maps the `dataSource` setting to a concrete `DataProvider`, and an app-level coordinator that rebuilds the handler (and clears the cache) when the source or endpoint setting changes.

- Alternatives: injecting one provider at launch (rejected - changing the source would need a relaunch); passing the provider down from `ViewController` (rejected - keeps wiring in the view, which Phase 3+ needs to replace).

### Decision: Attach a provider-capability descriptor
Give `DataProvider` a small capability descriptor so consumers can ask what the active source supports (at minimum: grid requests and clusters) instead of assuming both sources are interchangeable.

- Rationale: the HTTP source cannot serve grid data; a silent assumption would produce empty maps. `ios-data-modes` uses the descriptor to gate grid selection.
- Alternatives: hard-coding "HTTP means no grid" at each call site (rejected - duplicates the rule); unifying the payloads so both support grid (rejected - invents backend behaviour that does not exist).

### Decision: Cache in the handler layer, keyed by a value-typed `Parameters`
Convert `Parameters` to a `struct` conforming to `Equatable`/`Hashable`, and hold a `DataCache` (a bounded-TTL map keyed by `Parameters`) in the data-handler layer, matching Android's placement in `MainDataHandler`.

- Rationale: a cached result must be shared across providers and is meaningless inside a single provider; the HTTP provider must still run its incremental accumulation on a cache miss.
- TTL: five minutes, matching Android's `DataCache.DEFAULT_EXPIRY_TIME`.
- Alternatives: a `CachingDataProvider` decorator (rejected - it would sit below the accumulation state and could cache a partially accumulated HTTP result); caching inside each provider (rejected - duplicates TTL logic and defeats source switching).
- Consequence: `Result` is a `class`; cached entries are shared by reference. This change treats `Result` as immutable and does not mutate delivered results, and notes the option to convert it to a `struct` later.

### Decision: Reject stale results by reference timestamp, not a sequence number
Remember the reference timestamp of the last accepted result and drop any result whose reference timestamp is older.

- Rationale: iOS has no backend-supplied sequence number, and Android's `SequenceValidator` guards the *order in which locally-numbered events reach the UI*, not backend freshness - so porting it literally would not reject an older backend response. The reference timestamp is the only freshness signal common to both sources.
- Alternatives: port `SequenceValidator` verbatim (rejected - no sequence source, so it would always reject or always accept); compare strike counts (rejected - not monotonic).

### Decision: Store credentials in a separate credential store backed by the Keychain
Keep non-secret settings (`dataSource`, `serviceEndpoint`) in `SettingsStore` and put username/password behind a `CredentialStore` protocol with a Keychain implementation for the app and an in-memory implementation for tests.

- Rationale: secrets never enter `UserDefaults` or a preferences export by accident, and tests do not touch the Keychain.
- Alternatives: `UserDefaults` like Android (rejected - security); Keychain calls inline in the HTTP provider (rejected - untestable).

### Decision: Derive the user agent once from bundle metadata
Build the value `bo-ios-<CFBundleVersion>` from the app bundle's `CFBundleVersion` and apply it through one shared request-header helper used by both providers, replacing the literals in `JsonRpcClient` and any header setup added for HTTP.

- Rationale: mirrors Android's `bo-android-<longVersionCode>` (Android uses the version code; iOS has no equivalent, so the build number plays that role) and requires no per-build code change.
- Alternatives: a compile-time constant (rejected - drifts from the bundle); reading `CFBundleShortVersionString` (rejected - marketing version, not the build number the user asked for).

### Decision: The HTTP provider owns its incremental accumulation
Implement the HTTP provider to fetch per-minute strike logs over the requested interval, iterate in bounded chunks, accumulate strikes, expire those outside the window, and track the latest fetched minute - all internal state reset when the provider is created for a new configuration.

- Rationale: matches the reference provider, whose accumulation cannot be expressed by the current single-fetch contract.
- Alternatives: stateless per-request fetch (rejected - would re-download the whole window each poll and diverge from the reference); caching the accumulation in the handler (rejected - it is provider-specific state).

## Risks / Trade-offs

- **Plain-HTTP host blocked by ATS** → Add a `data.blitzortung.org` exception alongside the existing `tryb.de` entry, and confirm with the maintainer whether a production HTTPS endpoint exists.
- **Chatty per-minute fetching is slow** → Bound the chunk size and window as Android does, apply network timeouts, and surface the fetch through the existing lifecycle events so the status line can show progress.
- **Backend log format drift** → Parse defensively and cover each provider with fixture-based unit tests, keeping the provider contract in step with `bo-android`.
- **`Parameters` class-to-struct conversion ripples** → Source-compatible at call sites that pass instances, but `TimeIntervalWithOffset` conformance and `Result`/`StrikeOverlay` call sites must be checked; the Phase 0 suites cover the value behaviour.
- **Cache serving stale data after a source change** → Clear the cache and recreate the handler whenever the source or endpoint setting changes.
- **Keychain unavailable in some test contexts** → Inject the credential store and default to the in-memory implementation in tests.

## Migration Plan

- Ship behind the existing defaults (`dataSource = "rpc"`, `serviceEndpoint = ""`), so behaviour is unchanged until a user picks HTTP or sets a URL; the RPC provider keeps its built-in endpoint, now sourced from a provider default table rather than `ViewController.defaultServiceEndpoint`.
- Remove the hard-coded endpoint and user-agent literals in the same change so there is exactly one place a request header is built.
- Rollback: revert the change and the app returns to the Phase 0 single-RPC-provider behaviour; nothing is persisted that cannot be ignored (an unused `dataSource` value simply resolves to the default provider).
